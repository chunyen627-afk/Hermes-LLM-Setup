# 推測解碼（speculative decoding）比較

實測 MTP vs DFlash 在 32GB VRAM 上的取捨。

---

## 原理

一般生成每個 token 都要把整個模型的權重從 VRAM 讀一遍 ——
**瓶頸是記憶體頻寬，不是算力**。

推測解碼的做法：讓小模型先猜幾個 token，大模型**一次驗證整批**。
驗證 N 個跟生成 1 個的成本幾乎一樣（都只讀一次權重），所以猜對就賺到。

**輸出品質完全不變**（猜錯就丟掉重算），純粹省時間。

| 方式 | 怎麼猜 |
|---|---|
| **MTP** | 模型內建的預測頭，自迴歸一個一個猜（猜 3 個要算 3 次） |
| **DFlash** | 用 block diffusion **一次吐出整塊**（8-16 個），只算 1 次，而且看得到目標模型的 hidden states |

---

## 實測結果（RTX 3070 8G + 3060 12G × 2 = 32GB）

同一題（寫 CRC16-CCITT 函式，400 tokens）：

| | ctx 上限 | 生成速度 | 接受率 | 每次採納 |
|---|---|---|---|---|
| **MTP**（採用） | **176K** | 7.8 tok/s | 43% | 3 猜中 1.3 |
| DFlash v1 | **96K** | 13.8 tok/s | 15.6% | 8 猜中 2.11 |

**DFlash 快 1.8 倍，但 context 少 45%。**

> 有趣的是 DFlash 接受率更低卻更快 —— 因為它「猜得多、算得少」。

---

## ★ MTP 接受率複測（2026-08-20，乾淨環境）

上面那個 43% 是**受干擾的數據** —— 當時有第二台機器同時在用同一個 llama-server，
兩邊搶 slot 導致 KV cache 反覆重算，統計被污染。

單機獨佔後重測（ctx 180224、`--spec-draft-n-max 3`、固定 prompt 撐到各 ctx 位置）：

| ctx | 生成 tok/s | prefill tok/s | MTP 接受率 |
|---|---|---|---|
| 8K | 28.0 | 496 | **84%** |
| 30K | 25.9 | 477 | **88%** |
| 70K | 20.6 | 334 | **85%** |
| 120K | 16.7 | 298 | **75%** |

**真實接受率是 84-88%，不是 43%。**

**結論：MTP 永遠開著。** 接受率要掉到 30% 以下才會變成負收益（驗證開銷大於省下的時間），
最差的 120K 還有 75%。生成速度 28 → 16.7 的衰退是 attention O(n²) 的正常成本，不是 bug。

**沒有踩到 upstream 的已知雷**：

| Issue | 症狀 | 我們有沒有中 |
|---|---|---|
| [#23658](https://github.com/ggml-org/llama.cpp/issues/23658) | 特定 ctx 值讓接受率崩到 16% | ❌ 沒中，180224 是安全值 |
| [#23322](https://github.com/ggml-org/llama.cpp/issues/23322) | SWA 架構接受率只有 35-37% | ❌ 沒中，我們有 84-88% |
| [#23752](https://github.com/ggml-org/llama.cpp/issues/23752) | Metal 上 MTP 全面負收益 | ❌ 不適用（CUDA） |

**MTP 是啟動參數，不會自動判斷。** `--spec-type draft-mtp` 一旦載入就固定，
llama.cpp 不會因為 ctx 變長自動關掉它，要換必須重啟 server。

**曾經的誤判**：log 裡看到 134K 時生成掉到 0.8 tok/s（正常 23.7），一度懷疑 MTP 在長
context 崩了。實測證明不是 —— 同樣 120K 乾淨環境有 16.7 tok/s，快 20 倍。
0.8 tok/s 的真兇是**兩台機器搶 slot** 造成的 KV 重算，見 `踩過的坑.md`。

---

## 為什麼最後選 MTP

因為**壓縮的代價遠大於速度收益**：

| 快取命中 | 該輪耗時 |
|---|---|
| 98% | 24 秒 |
| 74% | **240 秒** ← 差 10 倍 |

實際任務用到 **128K（73%）才觸發壓縮**。若 ctx 只有 96K 會更早、更頻繁壓縮，
而每次壓縮後 cache 歸零要重算幾萬 tokens。

**壓縮損失（10 倍）> DFlash 收益（1.8 倍）。**

### 但如果用途不同

| 用途 | 建議 |
|---|---|
| 短問答、審 code（顧問用途） | **DFlash 96K**，快一倍 |
| 長任務、多輪除錯 | **MTP 176K** |

## DFlash2：現在不能用

| 項目 | 狀況 |
|---|---|
| 模型 | ✅ 有 Qwen3.8-27B 專用（z-lab 官方，2.06GB Q8_0） |
| llama.cpp | ❌ **PR #27342 尚未合併**（2026-08 仍 open） |
| 錯誤訊息 | `wrong number of tensors; expected 81, got 58` |

`draft-dflash` 只吃第一代（81 tensors），DFlash2 是 58 tensors。

**其他框架也不通**：

| 框架 | DFlash2 | 為什麼用不了 |
|---|---|---|
| MLX | ✅ | 只跑 Apple Silicon |
| vLLM / SGLang | 只有 v1 | 要求各卡 VRAM 相同，你是 8/12/12 不對稱 |
| llama.cpp | ❌ | PR 未合併，但**唯一能跑不對稱多卡** |

## EAGLE-3：沒有相容模型

| 模型 | 有 EAGLE3 GGUF 嗎 |
|---|---|
| Qwen3-8B / 14B | ✅ |
| Qwen3.6-27B | ✅ |
| **Qwen3.8-27B** | ❌ |

drafter 必須跟目標模型同代同 tokenizer，不能混用。

而且 DFlash 本來就是為了超越 EAGLE-3 而設計的（官方說快 2-3 倍），
實測也符合這個方向。

## 什麼時候重新評估

**換卡到 44-46GB 之後**：

```
模型 17.9 + KV(176K) 3.0 + DFlash2 ~2.5 + 緩衝 2.5 ≈ 26GB
剩餘 18-20GB → ctx 可推到 300K+
```

那時 DFlash2 就是**純賺的 1.8 倍**，不用犧牲 context。

在 32GB 上，任何額外的 draft model 都會排擠 ctx —— 這是結構性限制，
不是哪一代 DFlash 的問題。

---

## 怎麼測（換硬體或新版本時重跑）

```bash
llama-server --model <主模型> \
  --spec-draft-model <drafter.gguf> \
  --spec-type draft-dflash --spec-draft-n-max 8 \
  --ctx-size <試不同值找上限> ...
```

**看接受率**：
```
grep "draft acceptance" <log>
# draft acceptance = 0.13981 (210 accepted / 1502 generated), mean len = 2.11
```

`mean len` 是每次真正採納幾個 token —— 那才是速度的關鍵，不是接受率百分比。

⚠ OOM 時看爆在哪張卡：
```
allocating 1408.00 MiB on device 0: cudaMalloc failed
```
`device 0` 就是第一張，據此調 `tensor-split`。但如果調了還爆，
就是**總量不足**，只能降 ctx。
