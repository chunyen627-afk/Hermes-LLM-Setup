# 推理強度（reasoning effort）設定

這是最容易搞錯、影響最大的一項。實測數據都在下面。

---

## 🔴 最重要：速度差 32 倍

同一句「說 ok」：

| 設定 | 耗時 |
|---|---|
| `low` | **2.5 秒** |
| `high` | **80 秒** |

而且 high 那次的 30 個 token **全部花在 thinking**，`content` 是空的。

實際案例：一個多輪硬體除錯任務，high 模式下單輪要 **740 秒**，
橋接器顯示 **0.3 tok/s**（正常是 15）。跑一整晚只完成幾輪。

---

## 哪些值可以用（模型 template 決定）

Qwen3.8 的 chat template 只接受三種：

```jinja
{%- if resolved_reasoning_effort not in ('xhigh', 'medium', 'low') %}
    {{- raise_exception('Unexpected reasoning effort ...') }}
{%- endif %}
```

| 值 | 結果 |
|---|---|
| `low` | ✅ |
| `medium` | ✅ |
| `high` | ✅（template 內部自動轉成 `xhigh`） |
| `xhigh` | ✅ |
| **`minimal`** | ❌ **HTTP 500** |
| **`max`** | ❌ **HTTP 500** |

⚠ **Hermes GUI 的推理強度選單有「最小」和「最高」，選了會直接失敗。**
而且 Hermes 收到 500 可能顯示成 `Connection error`，讓你以為是網路問題。

---

## ⚠️ Hermes GUI 的選單其實不生效

實測：伺服器啟動時設 `low`，請求裡帶不同的值：

| 請求帶的值 | 耗時 | thinking 長度 |
|---|---|---|
| `low` | 40 秒 | 358 字元 |
| `xhigh` | 33 秒 | 253 字元 |

**xhigh 沒有比較久也沒有想比較多** —— 如果真的生效，差距應該很明顯。

**結論：真正決定行為的是 llama-server 啟動時的 `--reasoning-effort`。**
GUI 選單只是把參數放進請求，被伺服器忽略了。

### 那 GUI 該設什麼

**跟伺服器設一樣的值**，理由不是因為它有作用，而是**避免自己搞混**。

❌ 不要設成「GPU 是 high，GUI 是 xhigh」這種組合 ——
實際跑 high，但你看 GUI 以為是 xhigh，出問題時會誤判。

---

## 該用哪個

| 任務類型 | 建議 | 原因 |
|---|---|---|
| **多輪除錯**（改→測→再改） | **`low`** | 每輪都要等你回報，high 會讓一晚只跑幾輪 |
| 問觀念、找原因 | `low` | 夠用，2-3 秒回應 |
| **一次寫完整個模組** | `high` | 品質差距真實（見下） |
| 閒聊、查資料 | `off` | 最快 |

### high 的品質確實比較好（單一封閉任務）

同一題（SPSC 環形緩衝區 + 測試 + 編譯驗證）：

| | `off` | **`high`** |
|---|---|---|
| 完成時間 | 376 秒 | ~1500 秒 |
| 測試結果 | 55 項錯 1 項 | **3098 項 0 失敗** |
| 程式碼 | 6669 bytes | **5339 bytes**（更精簡卻更正確） |

**但這是「一次寫完一個模組」的情境。** 換成多輪對話就完全不划算。

---

## 不重啟也能讓它深思

平常維持 `low`，需要仔細分析時**在 prompt 裡直接要求**：

```
先仔細分析可能原因，逐項排除後再給結論：<你的問題>
```

或

```
這題有幾個互相牽制的因素，請逐項評估後再回答
```

效果接近 high，而且**只有那一題慢**，其他輪次照樣快。
這比兩邊切換設定實際得多。

---

## ⚠️ reasoning-budget 沒有硬約束力

```
--reasoning-budget 2048
```

聽起來像上限，但實測 **budget 2048 照樣可以繞 18 分鐘**。

真正的思考迴圈防護只有一個：`--reasoning off`。

### 怎麼判斷陷入迴圈

查 `/slots`：

| 狀態 | 意義 |
|---|---|
| `n_prompt_tokens_processed` 持續增加 | 正常處理 |
| **`processed` 停住不動，但 `n_prompt_tokens` 一直漲** | **陷入思考迴圈**（它在自言自語） |

用 `4-WATCH.bat` 可以即時看到這個。

## 本 repo 的預設

`_bootmenu.ps1` 的選單：

```
[1] 韌體設計 (預設)   think=low   ← 10 秒後自動選
[2] 一般寫 code       think=off
[3] 深度推理 (很慢)    think=high  ← 單一大模組才用
[4] 長 context        208K
```

**預設是 low**，因為日常用途（多輪對話、除錯）low 的體驗好太多。
