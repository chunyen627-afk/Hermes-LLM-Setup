# 效能調校實測

硬體：RTX 3070 8G + RTX 3060 12G × 2 = 32GB
模型：Qwen3.8-27B-UD-Q4_K_XL

---

## 結論：現有配置已是最佳解

```
--ctx-size 180224          176K
--tensor-split 6,12,13
--batch-size 2048 --ubatch-size 512
--spec-type draft-mtp --spec-draft-n-max 3
--cache-type-k q4_0 --cache-type-v q4_0
--swa-full --checkpoint-min-step 0 --ctx-checkpoints 32 --cache-ram -1
```

實測：**生成 23.7 tok/s、prompt 處理 488 tok/s**

---

## 測過的組合

| 配置 | 結果 |
|---|---|
| **176K + MTP（現況）** | ✅ **23.7 tok/s** |
| 176K 無 MTP | 10.6 tok/s |
| 140K 無 MTP + batch 4096/1024 | 5.8 tok/s |
| 128K 只用兩張 3060 | ❌ OOM |
| 176K + batch 4096/ubatch 2048 | ❌ OOM |
| 176K + batch 4096/ubatch 1024 | ❌ OOM |

### 三個關鍵發現

**1. MTP 讓生成速度翻倍**

```
有 MTP：23.7 tok/s
無 MTP：10.6 tok/s
```

MTP 額外吃約 1.5GB VRAM，但**絕對值得**。不要為了多一點 ctx 而關掉它。

**2. batch size 開不大**

176K ctx 已經把 VRAM 吃滿，ubatch 提到 1024 就 OOM。
想開大 batch 必須犧牲 ctx，但實測那樣反而更慢（5.8 tok/s）。

**3. 兩張卡不夠跑這個模型**

拿掉 3070 只用兩張 3060（24GB）連 128K 都載不進去。
**三卡是必要的，8GB 沒有浪費。**

---

## 真正的瓶頸是 prompt 處理，不是生成

```
生成 130 tokens  →  5.5 秒
處理 34K prompt  → 70.8 秒   ← 慢 13 倍
```

每一輪都要先處理完 prompt 才開始生成。所以**感覺慢的主因是 prompt 重算**，
而不是模型吐字慢。

### 這代表 cache 命中率決定一切

實際觀察（橋接器的輸出）：

| 快取命中 | 重算量 | 該輪耗時 |
|---|---|---|
| 98% | 481 tokens | **24.7 秒** |
| 74% | 7,680 tokens | **240.8 秒** |
| 0% | 4,096 tokens | 很慢 |

**同樣的 context 大小，耗時差 10 倍**，差別只在 cache。

---

## cache 什麼時候會失效

| 情況 | 後果 |
|---|---|
| **連線中斷** | 對話重來，cache 歸零 |
| **context 被壓縮** | 壓縮後要重算幾萬 tokens |
| 開新對話 | 正常，但前幾輪會慢 |

所以**避免斷線**跟**避免頻繁壓縮**比調參數更有效。

---

## 連線中斷的兩種錯誤碼

橋接器會印這兩種，意義完全不同：

| 錯誤 | 意義 | 常見原因 |
|---|---|---|
| `WinError 10053` | **客戶端**主動斷線 | Hermes 等太久超時（單輪過長） |
| `WinError 10054` | **伺服器**關閉連線 | 伺服器重啟、或 llama-server 崩潰 |

⚠ **都不是網路品質問題**。實測 ZeroTier 連線 20 個封包 0% 遺失、延遲 0ms。

推理只傳文字（一輪幾十 KB），遠端跟本機速度一樣。**不需要為了效能改成本機跑。**

---

## 還能改善的（用法層面）

硬體調校已到極限，剩下的是使用方式：

1. **context 到 60% 就開新對話** — 避免壓縮造成的 cache 失效
2. **一次講完整需求** — 減少輪數
3. **think 用 low** — 單輪從 740 秒降到幾十秒，大幅減少超時斷線
4. **不要隨意重啟伺服器** — 每次重啟都清空 cache

## 測試方法（供日後換硬體時重測）

```bash
# 生成速度
curl -s http://127.0.0.1:8001/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"...","messages":[{"role":"user","content":"數 1 到 30"}],"max_tokens":150}'

# prompt 處理速度（用長 prompt）
# 計時 / usage.prompt_tokens = tok/s
```

判斷 OOM：看 `llama-server` 的 log
```
ggml_backend_cuda_buffer_type_alloc_buffer: allocating XXX MiB on device N: cudaMalloc failed
```
`device N` 就是第幾張卡爆掉，據此調 `tensor-split`。

⚠ 測試時每次重啟務必**等 VRAM 完全釋放**（`nvidia-smi` 看到接近 0），
否則會誤判成 OOM。我第一輪測試就因為這個得到六組假的 OOM 結果。
