# 長時間任務設定

要讓 agent 跑通宵（或幾小時的大任務），這些預設值一定要改。

---

## 🔴 max_turns —— 最容易踩的坑

**`max_turns` 是「單次 run 的工具呼叫迭代上限」，每收到一則你的訊息就重新計數，
不是整個 session 累計。**

Hermes 安裝時的值可能是 60 或 90（官方預設是 500）。

### 為什麼 60/90 不夠

以每次迭代約 2.5 分鐘估算：

| max_turns | 可跑時間 |
|---|---|
| 60 | 約 2.5 小時 |
| 90 | 約 3.75 小時 |
| **500** | **約 20 小時** |

一個複雜任務光探索階段就可能用掉 70 幾次工具呼叫。設 90 的話**半夜就停在那邊等你**，
剩下的時間全部空轉。

### 撞到上限會怎樣

那一輪 run 停下來，**不是崩潰、不會掉資料**。你打「繼續」就接著跑。
所以後果是「白白浪費一晚」，不是出錯 —— 但這正是最可惜的。

### 改法

`config.yaml` 約 566 行：
```yaml
  max_turns: 500
```

## 其他三項

### show_reasoning
```yaml
  show_reasoning: true      # 約 1001 行
```
看得到模型在想什麼。長任務時很重要 —— 卡住了才分辨得出是在思考還是繞圈。

### compression.threshold
```yaml
compression:
  enabled: true
  threshold: 0.80           # 預設 0.50
```

| threshold | 176K ctx 的觸發點 | 適合 |
|---|---|---|
| 0.50 | 90K | 保守，壓縮頻繁 |
| **0.80** | **144K** | **長任務**，晚點壓縮保留更多上下文 |

壓縮太早會丟掉有用的上下文；太晚則來不及。長任務建議 0.8。

### max_tool_calls
```yaml
code_execution:
  max_tool_calls: 100       # 預設 50
```
這是**單次 code execution** 內的 RPC 呼叫上限，跟 `max_turns` 不同層級。

### abort_on_summary_failure（若你的版本有）
```yaml
compression:
  abort_on_summary_failure: true
```
壓縮失敗時明確停下報錯，而不是默默撞牆。舊版沒這個選項。

## 通宵前的檢查清單

```bash
hermes config show
```

確認這幾項：

| 項目 | 應為 | 意義 |
|---|---|---|
| `Max turns` | **500** | 約 20 小時的量 |
| `context_length` | 跟伺服器一致 | 不一致會塞爆才發現 |
| `Compression Enabled` | yes | 快滿時自動壓縮 |
| `Threshold` | 80% | 長任務的合適觸發點 |
| `Reasoning` | on | 看得到思考過程 |

再確認伺服器端：
```bash
3-CHECK-CTX.bat <GPU主機IP>
```
`ctx 上限` 要跟 Hermes 的 `context_length` 一樣。

還有橋接器要開著（每 300 秒會印一行用量，可以據此判斷有沒有卡住）。

---

## 判斷「卡住」還是「在工作」

長任務跑很久時，用這兩個訊號分辨：

**橋接器視窗**
```
[ctx ] 94,208 / 180,224 (52%)  快取 95%  重算 1,548  推理中
```
- `推理中` 且數字有變 → 正常工作
- 長時間 `閒置` 且沒有新的推論行 → 可能真的停了

**GPU 主機端**（更準）
```bash
curl -s http://<IP>:8001/slots
```
看 `n_prompt_tokens_processed`：
- **持續增加** → 正常處理
- **停住不動但 `n_prompt_tokens` 一直漲** → 陷入思考迴圈，該中斷

⚠ 思考迴圈是 `--reasoning auto` 或 budget 太大造成的，見
[踩過的坑 #8](踩過的坑.md)。
