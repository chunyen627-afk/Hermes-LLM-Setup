# 驗證的紀律

**「我認為改對了」不是證據。**

這份講的是怎麼避免「宣告完成但其實沒好」——
那是最浪費時間的失敗模式，因為錯誤會被帶進下一個階段。

---

## 一、驗證標準怎麼訂

### 「數量對」不等於「內容對」

真實案例（2026-08-28）：驗證顯示畫面時數「亮點像素總數」，
得到 11,596 個，跟預期元素的估算吻合 → 判定「沒問題」。

實際那張圖：**整片是條紋，一個預期元素都沒有**。
亮點全來自條紋，數量剛好對得上。

**「該有的少了」和「不該有的多了」會互相抵消。**

### 好標準 vs 壞標準

| 壞 | 為什麼 | 好 |
|---|---|---|
| 總數、平均、統計量 | 細節被聚合掉 | 逐項比對已知正確值 |
| 「有輸出就算過」 | 輸出可能全錯 | 輸出的**內容**符合預期 |
| 「沒有錯誤訊息」 | 很多失敗不報錯 | 主動查詢狀態確認 |
| 「測試通過」 | 測試可能沒覆蓋到 | 測試**涵蓋了這個情境**才算數 |
| 單一指標 | 一個數字藏不住細節 | 多個獨立指標互相佐證 |

### 標準不是越嚴越好 —— 太嚴會做不完

**動手前先問：多準才算對？** 沒定義就開始，很容易一路加嚴到做不出來。

2026-08-29 燒掉四小時的實例：做 BF16 矩陣乘法加速器，題目要求
「跟 C 版本一致」，結果它拿 Python 的 `Fraction`（精確有理數）當標準。
**那比 C 還嚴格** —— C 的 `float a+b` 本身就有捨入誤差，不可能跟精確值一致。
等於在追一個連參考實作都達不到的目標。

**選標準的順序：從最鬆的開始，往上加到剛好夠用**

1. **應用層結果一樣**（生成的文字、辨識的類別、使用者看到的畫面）
2. **在容許誤差內**（相對誤差 < 1e-6 之類）
3. 跟參考實作**逐位元相同**
4. 跟數學上的精確值相同 ← 幾乎沒有場合需要這個

大多數工程問題停在 1 或 2 就夠了。跳到 3、4 之前先問
**「更準能換到什麼？」** —— 換不到東西就是浪費。

**另一個常見錯誤：拿自己寫的模型當標準。**
題目說「跟 X 一致」就真的去跑 X。用自己的參考實作比對，
等於自己出題自己改考卷 —— 模型跟受測物可能一起錯，而且錯得一致。
（相關：本檔「先驗證你的量測工具」那節）

### 反向檢查

問自己：**如果這個東西壞了，我現在的驗證會不會發現？**

不會的話，驗證等於沒做。

實例：測試「球掉了會扣球數」全過，但沒有測「球真的會掉」——
結果球卡在擋板上永遠不掉，遊戲沒有結束條件，26 個測試全綠。

## 二、什麼時候可以說「完成」

三個條件同時成立：

1. **有可重現的證據**（不是「我看起來覺得對」）
2. **證據涵蓋了需求的每一項**（不是只驗最容易驗的那項）
3. **失敗的情況也試過**（happy path 過不代表沒問題）

### 說「完成」之前的自我檢查

- 我驗證的是**真的東西**，還是我自己的假設？
- 如果現在有人說「這裡壞了」，我拿得出反駁的證據嗎？
- 我有沒有把「沒看到錯誤」當成「沒有錯誤」？

## 三、一次只改一件事

同時改多處，出問題就無法歸因。

真實案例（2026-08-28）：同時改了快取設定、繪圖邏輯、HUD 格式，
結果比改之前更糟（原本只是閃爍，變成兩份緩衝區內容完全不同），
而且分不出是哪個造成的，只能整批退回。

**規則**：

- 動手前先讓「已知能跑」的版本可回復（git commit / 複製一份 / 記下版本）
- 每次只改一件事，改完立刻驗證
- **驗證不過就退回**，不要在壞掉的基礎上疊新的改動
- 一個假設試三次沒過就換方向，並記下試過什麼

### 但如果同時有多個 bug，「一次只改一件事」會誤導你

真實案例（2026-08-29，Booth 乘法器）：54 個測試錯 53 個。
修好第一個 bug 之後，errors 只從 53 掉到 **52** —— 看起來幾乎沒用，
差點誤判成「第一個修正是錯的」而退回。實際上那個修正是對的，
只是還有第二個更根本的 bug（每一項沒乘上被乘數）蓋過了它。

**當改動幾乎沒有改善時，先問「是不是還有第二個 bug」，
而不是立刻否定剛才的修正。**

分辨方法 —— **建一個獨立的參考模型，先讓它 100% 正確**：

1. 用最快的語言（通常 Python）寫一份參考實作
2. **對它做窮盡或大量隨機驗證**（例：200k 隨機取樣，零失配）
3. 確定參考模型無誤後，再回頭比對受測物

這樣剩下的每一個失敗都**確定**是受測物的問題，不是你的期望值算錯。
先前 UART 那輪也是同樣的模式：in-sim checker 自己有 off-by-one，
害人懷疑錯對象。

## 四、先驗證你的量測工具

**懷疑資料不對之前，先確認量測方法是對的。**

實例：一開始以為「dump 出來的畫面是錯的」，於是往記憶體/時序方向查了很久。
後來畫一張**已知內容的測試圖案**（四象限各一個固定顏色），
dump 回來逐格比對 —— 完全吻合，證明 dump 方法可信。
真正的問題在別的地方。

**做法**：餵一個你完全知道答案的輸入，看量測結果對不對。
對了才開始查真正的問題。

反過來說，如果工具本身會間歇性失敗（例如某個 API 有 30% 機率回錯誤），
**要先知道這件事**，否則會把工具的失敗當成資料的異常，
在錯誤的前提上推理很久。

---

## 五、給 AI agent 的補充

**你看不到的東西，不要假裝看到。**

- 沒有畫面就說「我看不到，我根據 X 推理」，不要說「應該正常」
- 使用者回報的現象是**第一手資料**，比你的推論可信
- 使用者說「還是壞的」，那就是還是壞的，不要辯解

**工具失敗要重試，不要當成資料異常。**

**看到 `[SKILL_PRUNED]` 或類似的截斷標記** = 「這份資料我現在沒有」，
動手前重新載入，不要憑印象做。
