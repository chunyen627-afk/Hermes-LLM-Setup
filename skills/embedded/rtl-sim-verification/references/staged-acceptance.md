# 分階段驗收標準

**什麼時候該驗什麼。** 順序錯了會發生兩件事：
太早驗 → 在還會被改掉的東西上花時間；
太晚驗 → 一次面對三層的 bug，分不出是哪一層錯。

硬體跟軟體最大的差別在**回饋速度**：
軟體跑一下就知道對不對，錯誤訊息直接指到行號；
硬體「模擬跑完了」不代表對，而且沒有任何東西會告訴你
**「你這輪只驗了一半」**。所以每個階段的出場條件要事先寫死，
不能等做完再自己判斷。

---

## 階段總覽

| # | 階段 | 驗什麼 | 出場條件（必須是機器可判定的） |
|---|---|---|---|
| 0 | 定標準 | 還沒寫任何 RTL | 誤差範圍、參考實作、驗收清單都已寫進文件 |
| 1 | 純功能 | 數值 / 邏輯對不對 | 對外部參考 N 筆比對，`n_checked > 0` 且 0 bad |
| 2 | 介面契約 | 握手、反壓、邊界 | 協定 assertion 零觸發 + **每個情境都真的跑到** |
| 3 | 整合 | 模組串起來還對嗎 | end-to-end 對參考實作，且子模組驗收仍全綠 |
| 4 | 時序/資源 | 收不收得了斂 | 合成 + STA 報告（沒工具就標 `[ASSUMPTION]`） |

**不要跳階段。** 第 2 階沒過就進第 3 階，症狀會是
「整合之後偶爾錯幾筆」——那是最難查的一類 bug。

---

## 階段 0：動手前先定標準

**這階段不寫 RTL。** 產出是文字，不是程式碼。

必須先回答（答不出來就是還沒想清楚）：

1. **參考實作是誰？** —— 必須是**外部的**。
   題目說「跟 C 版本一致」就真的去編譯那份 C，
   不要拿自己寫的模型當標準（自己出題自己改考卷，
   模型跟 RTL 可能一起錯而且錯得一致）。
2. **多準才算對？** —— 見 [[hardware-design-tradeoffs]] 的精度表。
   從最鬆的標準開始往上加，不要預設「位元精確」。
3. **這個 block 的介面契約是什麼？** ——
   幾條通道、誰給反壓、outstanding 上限、對齊/邊界規則。
   **寫下來**，因為第 2 階要照這份清單驗。
4. **哪些情境「一定要跑到」？** ——
   這就是 `require_cover` 的清單。現在定，不是測完再補。

### 測試資料：能拿到真的就用真的

題目提到具體的模型、資料集、檔案時，**先花十分鐘去拿真的**。
真實資料會暴露隨機值不會暴露的東西：
實際的數值分布、特殊值（0、極小值、重複樣式）、真實的維度。

**拿不到才用隨機值 —— 但必須把這件事標出來。**

☠ 2026-08-30 實際發生的：下載 llama2.c 的模型檔失敗，
`ext/llama2.c` 的內容字面上就是 **`404: Not Found`**。
於是改用 `rand_bf16()` 產生隨機權重繼續做 ——
**但報告和 HANDOFF 裡完全沒提這件事**。
任何人讀那份文件都會以為 288/288 是拿真模型跑的。

問題不在用隨機值（這個專案裡隨機值反而更嚴格），
**問題在失敗被默默吐掉。**

規則：

- 下載失敗、檔案拿不到、工具裝不起來 ——
  **這些都要寫進文件，不是找個替代方案就算了**
- 用了取代品就標 `[ASSUMPTION]`，寫清楚「真的是什麼、
  我用的是什麼、差別在哪」
- 報告數字時要帶條件：「在隨機 BF16 資料下 288/288」
  跟「288/288」是兩句不同的話

這跟總則那條「報告要寫在什麼條件下通過」是同一件事。

### 規格承諾的東西要列進 `spec` 區塊

**gate 擋得住「測試沒跑」「路徑沒走過」，
擋不住「規格書上有、程式碼裡沒有」。**

原因很簡單：**沒實作的東西不會有測試失敗，因為根本沒人替它寫測試。**

☠ 2026-08-30 實際發生：架構文件定義了 8 個暫存器，
實作只做了一半 —— `CTRL.reset`、`CTRL.bf16_in`、
`STATUS.error`、`COUNT` 四項完全沒有。
**而 gate 是綠的**，因為測試只測了有實作的那些。
主控那側若照文件寫驅動程式，會讀到不存在的東西。

寫法（`simcheck.json` 的 block 裡）：

```json
"spec": {
  "CTRL.reset":   {"pattern": "ctrl_reg\[1\]|soft_reset",
                   "in": ["rtl/matmul_top.v"],
                   "why": "ARCHITECTURE.md 0x00 bit1"},
  "COUNT":        {"pattern": "COUNT|count_reg|out_count",
                   "in": ["rtl/matmul_top.v"],
                   "why": "ARCHITECTURE.md 0x1C 已產生幾筆輸出"}
}
```

每一項都要寫 `why`（指向文件的哪一行）——
之後爭論「這個到底要不要做」時，那句話就是依據。

**規則跟 `require_cover` 一樣：只能加不能減。**
真的不做就**改文件**，不要讓兩邊不一致 ——
文件跟實作對不上時，唔一邊錯了沒人知道。

順帶一提：文件裡的**數字**也會不同步。
同一輪發現 `ARCHITECTURE.md` 寫 `MAX_RD_BURSTS = 4`（還附了選 4 的理由），
程式碼實際是 16。這種也可以用 `spec` 盯。

### 別把題目拆掉之後就忘了最外層

同一輪還發生了兩件同類的事：

- 題目說「配合 llama2.c 跑 tinystories 15M」，
  實際只證明了 **matmul 這一個運算**跟 C 版本一致
- 架構圖畫了 xSPI→AXI bridge，那個方塊到最後都是空的，
  而且它自己的待辦清單裡從來沒列過

**拆解子問題是對的，但做完子問題不等於題目做完了。**

防堵：階段 0 列 block 時，**把架構圖上每一個方塊都列進去**，
不做的明確標 `status: skipped` 加理由，不要留白。
收尾時再拿原題目對一次：「它要的東西，我都交了嗎？」

### 怎麼把 `simcheck.json` 生出來（照做，不要憑印象）

**第一步：複製範本。**
```bash
cp C:/Users/pjunm/AppData/Local/hermes/skills/embedded/rtl-sim-verification/references/simcheck.example.json    ./simcheck.json
```
把裡面的 block 換成這個專案的，`status` 全部設 `pending`。

**第二步：切 block。** 一個 block = 一個能單獨驗的模組。
判準是「**它有沒有自己的 testbench**」——需要別的模組才能測的，
那是整合（階段 3），不是獨立 block。

**第三步：對每個 block 推導 `require_cover`。**
不要憑印象列，照這五個問題逐一問，每個「有」就是一個 cover：

| 問題 | 有的話就加 cover |
|---|---|
| 這個介面**誰可以喊停**？（valid-ready、full/empty、busy） | `backpressure` — 反壓真的發生過幾拍 |
| 有沒有**數量上限**？（outstanding、FIFO 深度、burst 長度） | `<name>_max` — 壓到上限過幾次 |
| 有沒有**邊界規則**？（4KB、對齊、繞回、進位） | `boundary_cross` — 真的跨過去幾次 |
| 有沒有**錯誤路徑**？（錯誤回應碼、逾時、非法輸入） | `error_response` — 錯誤真的發生過幾次 |
| 有沒有**只在特定時序才出現的情況**？（背靠背、同時、reset 中途） | `back_to_back` / `reset_during_traffic` |

再加一個檢查：**這個 block 對外依賴什麼？那個東西的真實行為我模擬了嗎？**
（延遲會變、會反壓、會突然停很久 —— 見總則）
每一項也是一個 cover。

**第四步：寫 `_cover_meanings`。**
每個 cover 都要寫「為什麼要測它」，一句話。
寫不出理由的 cover 就刪掉；寫得出來的，那句話就是未來爭論時的依據。

**第五步：確認每個 block 都有 `run_in`（如果 TB 讀相對路徑的資料檔）。**
`$readmemh("x.hex")` 在錯的目錄跑會**每一筆都 mismatch，看起來完全像 RTL 壞掉**。
這個坑值得預先寫進設定檔，不要等踩到。

**產出**：`simcheck.json`（全部 `status: pending`）+ 架構文件裡的精度標準。

> ⛔ **`simcheck.json` 要在寫第一行 RTL 之前就存在。**
> 常見錯誤：先寫 RTL，等模擬失敗才開始想「怎樣算對」——
> 那時候標準會不自覺地被寫成「剛好讓現在這版通過」。
>
> 判斷有沒有寫早：**如果你已經知道設計長什麼樣才列得出 cover，就太晚了。**
> cover 應該從「介面契約」推出來，不是從「我寫了什麼」推出來。

## 階段 1：純功能

**只驗數值 / 邏輯，不管時序、不管介面。**

- 純組合或最簡單的時序，先把功能做對
- 對照**外部參考實作**逐筆比對
- 測試向量要**大量而且隨機**（幾萬筆），不是手挑五個

**出場條件**：
```
CHECK <name> <n_checked> <n_bad>     n_checked 夠大、n_bad = 0
```

⚠ **`n_checked` 一定要印出來並且自己確認合理。**
0 筆通過不是通過（向量檔沒產生、`$fscanf` 讀不到，
迴圈一次都沒進去，結果印 PASS）。

⚠ **看失敗模式，不要只看錯誤數**。
`0 × 0 = 0` 通過不代表任何事——那是唯一「不管移位錯幾位都得 0」的案例。
`1×1` 得 2 → 差 factor of 2 → 移位錯；
`A×B` 得到接近 B 的值 → 根本沒乘上 A。

**這階段不要切 pipeline。** 功能對了再切，
否則同時 debug 數值和時序兩件事。

## 階段 2：介面契約

**這是最容易被跳過、也最容易出事的一階。**

功能對了不代表接得上。這階段驗的是**握手行為**，
而握手的錯不會顯示成錯誤數值，會顯示成
「卡住」「資料重複」「偶爾少一筆」——很容易被誤判成測試環境的問題。

### 先驗你的測試對手

驗 master 要有 slave，驗 producer 要有 consumer。
**那個對手是你自己寫的、未驗證的程式碼。**
先用已知正確的刺激打它一遍（不透過 DUT），它自己過了才有資格當標準。

### 對手模型要像真實器件，不是只要「能回應」

⚠ **這條最容易整組漏掉，而且漏掉時測試會全綠。**

一個陣列 + 固定延遲 + `ready` 恆為 1 —— 能跑、資料也對、測試全過。
但那證明的是「**在一個永遠很快、延遲固定、不會反壓的對手下，
資料路徑算得對**」，不是「接上真東西會動」。

真實器件會做的事，理想模型都沒有：延遲抖動、週期性長停頓
（DDR4 的 refresh、匯流排讓出）、佇列滿時反壓、讀寫轉向損失、
亂序回應。

**規則：對手模型只能變難，不能為了讓測試過而變簡單。**
加了這些之後測試掛掉是**發現了 bug**，不是模型寫壞。

⚠ 加反壓時，**取樣邏輯要跟著改**：只在 `valid && ready` 那拍取樣並前進。
只改 `ready`、不改取樣，會跑出一堆錯而讓你誤判 DUT 壞掉
（2026-08-30 我自己踩過這個坑）。

為難清單、COVER 寫法和那個取樣陷阱見 `protocol-interface-verification.md`。

### 每一項都要有對應的 COVER

| 情境 | 為什麼一定要測 |
|---|---|
| 單筆交易 | 基本盤 |
| **背靠背**（前一筆回應沒回就發下一筆） | 沒測 = 管線化從沒被驗證 |
| **反壓**（`valid && !ready`） | **`ready` 恆 1 等於完全沒測反壓** |
| 邊界 / 對齊拆分 | 協定硬性規定（如 AXI 的 4KB） |
| outstanding 壓到上限 | 上限守不守得住 |
| 錯誤回應碼 | SLVERR / NACK 有沒有被往上報 |
| reset 在傳輸中途 | 復原後狀態乾不乾淨 |

**出場條件**：
```
ASSERT <name> 0        所有協定 assertion 零觸發
COVER <name> <n>       上表每一項 n > 0
```

反壓那項要真的隨機拉低 ready 才數得到：
```verilog
always @(posedge clk) ready <= ($random % 100) < 70;   // 70% 接受
```

⚠ **「所有比對 0 bad」不是出場條件。**
資料全對但反壓從沒發生過，代表那條路徑完全沒走過。
`--require-cover` 就是為了擋這個。

完整方法在 `protocol-interface-verification.md`。

## 階段 3：整合

**每接一個模組就驗一次，不要全部接完才測。**

- 接上去之前，**子模組的階段 1 / 2 驗收要還是綠的**
  （改介面很容易把已經驗過的東西弄壞）
- 整合後的驗收對象是 **end-to-end 對外部參考實作**，
  不是「子模組都過了所以整體沒問題」
- 資料真的走了完整路徑嗎？
  例：權重是真的從記憶體讀進來，還是 TB 偷偷 `$readmemh` 灌進去的？
  **這要有自己的 COVER**（`weights_from_ddr`），
  否則整合測試可能繞過了整條資料路徑

**出場條件**：
```
CHECK end_to_end <n> 0
COVER <每條真實路徑都走過> <n>   n > 0
```
且子模組的 gate 重跑仍然全綠。

⚠ **整合階段最常見的錯**：為了讓整合測試過，
回頭改子模組去遷就測試環境。
改之前先問：**測試環境完美的話，我還會做這個改動嗎？**
（判斷準則見主 SKILL.md 的「測試環境壞掉時，改哪一邊」。）

## 階段 4：時序與資源

模擬跑得過不代表做得出來。

- 合成（yosys / Vivado）→ 有沒有推出 latch、有沒有不可合成的寫法
- STA → 目標頻率收不收得了斂
- 資源報告 → DSP / BRAM / LUT 夠不夠

**沒有工具的時候**（只有 iverilog）：
這階段**做不了，就誠實標注**。

```markdown
[ASSUMPTION] 目標 75MHz 可收斂 —— 本機無 Vivado，未驗證。
[ASSUMPTION] MIG AXI 寬度 = 256 —— 需在 Vivado 確認。
```

⚠ **不要把「模擬過了」寫成「設計完成」。**
時序未驗證就是未驗證，寫進文件比藏起來好——
藏起來的話下一輪（或接手的人）會當成已知事實往下做。

## 沒有人在旁邊時，怎麼自己收尾

長時間自主開發時，沒有人會告訴你「你這輪只驗了一半」。
所以**宣告完成之前，這套流程要自己跑一遍**。

### 宣告完成前的四道自檢

**1. 跑 gate，不要自己讀 log 判斷。**
```bash
python C:/Users/pjunm/AppData/Local/hermes/skills/embedded/rtl-sim-verification/references/scripts/simcheck.py --config simcheck.json --all
```
exit 0 才算完成。**exit 1 就是還沒好**，不管 log 看起來多漂亮。

**2. 每個 `CHECK` 的比對數要合理。**
`0 checked, 0 bad` 是失敗不是通過。數字太小也可疑 ——
「應該跑幾筆」心裡要有個數，對不上就是測試沒真的跑。

**3. 自己做一次變異測試。**
在 DUT 裡蓄意注入一個 bug（把某個賦值 XOR 1、位址偏一格），
重跑測試 —— **抓不到就代表測試是空轉的**。

```bash
sed "s/out <= data;/out <= data ^ 32'd1;/" rtl/foo.v > /tmp/mut.v
# 重編、重跑，確認 CHECK 的 n_bad 變大
```

⚠ **先確認注入成功**（`grep` 一下改到了沒），
否則你跑的是未修改的原始碼，會得到一個假的「測試沒抓到」或假的通過。

**4. 報告要寫「在什麼條件下通過」。**
「288/288 一致」和「在固定延遲、無反壓的記憶體模型下 288/288 一致」
是兩句不同的話。後者才誠實，而且接手的人不會誤判。

### 卡住時的自我診斷

**改完之後結果完全沒變** = 改的不是根因，或改到一半。
這時候不要接著改下一個地方 —— 先讓那個修正在 log 裡留下痕跡
（印出它算出來的值），確認真的生效了再往下走。

**多個測試同時爛掉** = 先數一遍總共幾個錯、分佈在哪幾個 test，
**最先壞的通常是根因**，後面往往只是下游效應。
不要只讀 log 尾巴，也不要只 grep 自己關心的訊號。

**測試環境看起來壞了** = 先問「測試環境完美的話，我還會做這個改動嗎？」
答案是「不會」就去修測試環境，不要改設計去遷就它。

### 接手文件要寫什麼

context 會被壓縮，你會忘記自己三小時前做過什麼。
`HANDOFF.md` 要在 ctx 到 60% 之前更新，重點順序是：

1. **已經確認行不通的做法**（最重要 —— 不寫下來，下一輪會重試一遍）
2. 現在卡在哪、下一步是什麼
3. 關鍵決定與理由（為什麼選這個架構、為什麼是這個數字）
4. 未驗證的假設，全部標 `[ASSUMPTION]`

第 1 項尤其值得花時間。**踩過的坑不寫下來，等於沒踩過。**

## 每個階段共通的三條規則

1. **出場條件必須是機器可判定的。**
   一旦標準變成「你自己看看對不對」，答案永遠是「看過了，很好」。

2. **驗收標準只能加，不能為了讓測試過而拿掉。**
   真的不適用，就把理由和日期寫進「已確認行不通的做法」再拿掉。

3. **先數一遍再決定追哪個。**
   多個測試同時爛掉時，**最先壞的通常是根因**，
   後面的往往只是下游效應。不要只讀 log 尾巴，
   也不要只 grep 自己關心的那個訊號——
   會錯過旁邊更大的破口。

## 對照：這套流程擋掉的實際錯誤

| 沒有階段標準時發生的事 | 哪一階會擋掉 |
|---|---|
| 追 Python `Fraction` 精確有理數，燒掉六小時 | 階段 0（先定精度標準） |
| 測試印 `0 checked, 0 mismatches` 然後 PASS | 階段 1（`n_checked > 0`） |
| 讀取路徑 63 筆全錯，三輪都沒發現 | 階段 2（先數總 error 分佈） |
| 為了遷就壞掉的 memory model 改 DUT 設計 | 階段 2（先驗測試對手） |
| 反壓從沒測過，整合後偶爾掉資料 | 階段 2（`COVER backpressure`） |
| 「模擬過了」被當成「可以下線」 | 階段 4（`[ASSUMPTION]` 標注） |
| 用理想 SRAM 當 DDR4，測全綠但反壓路徑是壞的 | 階段 2（對手模型要像真實器件） |
