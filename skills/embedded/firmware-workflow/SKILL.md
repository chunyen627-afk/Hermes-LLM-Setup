# 韌體開發的通用流程

不管是 STM32、ESP32、還是別的 MCU，這些原則都適用。
晶片專屬的細節看對應的 skill。

---

## 一、分層驗證：先在快的地方驗完

每個韌體專案都有快慢迴圈，**慢迴圈的成本是快迴圈的幾十倍**：

| 層 | 一次多久 | 抓得到什麼 |
|---|---|---|
| **1. 主機端編譯跑邏輯** | 秒 | 演算法、狀態機、資料結構（**多數 bug 在這**）|
| **2. 交叉編譯** | 十秒~分鐘 | 型別、對齊、不可用的標準函式庫 |
| **3. 燒錄 + 跑** | 分鐘 | 啟動流程、時鐘、周邊初始化 |
| **4. 真實負載** | 更久 | 時序、中斷競爭、記憶體壓力 |

**把「跟硬體無關的部分」抽出來**（繪圖、協定解析、狀態機、演算法），
在 PC 上用 gcc 編起來測。跑得比燒錄快幾百倍，還能用 debugger。

實作方式：硬體存取包成薄薄一層介面，主機版給假的實作
（寫進陣列而不是暫存器）。

---

## 二、怎麼證明「它真的在跑」

**「編譯過了」不等於「在跑」。** 燒進去看起來沒事，可能根本卡在初始化。

要有**機器可讀的證據**，不要只靠肉眼看板子或 LED：

| 方法 | 怎麼做 |
|---|---|
| **RAM 計數器** | 全域變數 `g_frames++`，用 SWD/JTAG 隔幾秒讀兩次，數字有跳才算在跑 |
| **序列埠 log** | 印狀態機階段、關鍵數值，主機端存檔 |
| **framebuffer dump** | 有螢幕的話直接把顯示記憶體讀回來轉 PNG（見 [[embedded-ui-verification]]）|
| **心跳腳位** | GPIO 翻轉，用示波器或另一塊板子量 |

⚠ **讀 RAM 變數時不要 halt CPU** —— halt 住就永遠讀到初始值，
會誤判成「程式沒跑」。（STM32 是 `mode=0`，其他平台要查對應設定。）

## 二之二、驗證標準怎麼訂（最容易搞砸的地方）

**「數量對」不等於「內容對」。**

2026-08-28 實例：模型驗證顯示畫面時用「亮點像素總數」——
數出 11,596 個，跟預期的（球+拖尾+掃描線+點環）吻合，於是宣告「乾淨、沒有毀損」。

實際看那張圖：**整片是條紋，一個動畫元素都沒有**。
那 11,596 個亮點全是條紋造成的，數量剛好對得上。

### 訂驗證標準的原則

| 壞的標準 | 為什麼壞 | 好的標準 |
|---|---|---|
| 亮點總數 | 「該亮變黑」和「該黑變亮」互相抵消 | 特定座標的顏色是否符合預期 |
| 「有輸出就算過」 | 輸出可能全錯 | 輸出跟已知正確值逐項比對 |
| 「沒有錯誤訊息」 | 很多失敗不報錯 | 主動讀回驗證 |
| 單一數字 | 一個數字藏不住細節 | 多個獨立指標互相佐證 |

### 畫面類的驗證，一定要真的看

數值統計會騙人。**dump 成 PNG 之後要用 vision 真的看過**，
而且問具體問題：

```
背景是什麼顏色？（對照預期）
有幾個圓形元素？位置在哪？
有沒有不該存在的東西（條紋、雜點、色塊）？
畫面上的文字內容是什麼？（HUD 格式壞掉很常見）
```

不要問「這張圖正常嗎」——那太寬鬆，模型會說正常。

### 雙緩衝要兩塊都驗

只驗一塊會漏掉「兩塊內容不一致」這類問題。
**正常情況下兩塊應該非常相似（只差一幀）**，
如果連底色都不同，那是嚴重的邏輯錯誤。

## 二之三、一次只改一件事

同時改多處，出問題就無法歸因。

2026-08-28 實例：同時改了 MPU 快取設定、繪圖邏輯、HUD 格式，
結果畫面比改之前更糟，而且分不出是哪個造成的
（原本只是條狀閃爍，改完變成兩個緩衝區內容完全不同）。

**規則**：
- 有一個「已知能跑」的版本就先存起來（git commit 或複製一份）
- 每次只改一件事，改完立刻驗證
- 驗證不過就退回，不要在壞掉的基礎上繼續改
- **「修好了」要有證據**，不能只是「我認為改對了」

---

## 三、除錯策略

### 控制變因

症狀出現時**不要一次改很多東西**。設計能區分假設的實驗：

實例（2026-08-28 STM32 LTDC 雜點）：
```
純 DMA2D 畫測試圖案      → 乾淨    ⇒ DMA2D 沒問題
DMA2D + CPU 畫圓        → 毀損    ⇒ 問題在兩者互動
                                  ⇒ 快取一致性
```
兩個實驗就把範圍從「整個顯示路徑」縮到「D-Cache 設定」。

### 先驗證你的量測工具

**懷疑資料不對之前，先確認量測方法是對的。**

同一個案例：一開始以為「dump 出來的畫面是錯的」，
後來畫一張**已知內容的測試圖案**（四象限各一個固定顏色），
dump 回來逐格比對 —— 完全吻合，證明 dump 方法可信，
真正的問題在別處。

如果沒做這步，會在錯誤的前提上推理很久。

### 同一個錯誤試三次沒過就換方法

不要在同一條路上鑽。換方法之前把試過什麼寫下來，
避免之後又繞回來。

---

## 四、燒錄

- **燒完要驗證真的進去了** —— 讀回第一個字（通常是初始 SP 或 magic），
  值不對就是沒燒進去，不要往下做
- **有些工具失敗不報錯** —— 例如漏了外部 flash 載入器，
  CLI 會顯示成功但實際沒寫入。要看輸出裡的容量/位址對不對
- **兩段式的板子**（內部 flash 太小、程式跑在外部 flash）
  要分別燒 bootloader 和 app，漏一個就跑舊的

---

## 五、跨 session 的知識保存

**壓縮會把 skill 內容剪成 `[SKILL_PRUNED]`。**
動手前若看到那個標記，一定要 `skill_view` 重新載入，不要憑印象做。

**踩到坑就當場寫進 skill**（`skill_manage(action='patch')`），
不要等做完才整理 —— 做完時 context 已經壓縮好幾輪，細節記不得了。

發現 skill 內容是錯的**也要當場改**。
（實例：原本寫「PSRAM 設 write-through」，實測要 non-cacheable 才對。）
