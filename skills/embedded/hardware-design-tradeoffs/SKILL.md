# 硬體設計的取捨

寫軟體時「先做對再最佳化」通常成立，因為改一行重跑就好。
**硬體不是** —— 精度、位寬、pipeline 深度、記憶體階層這些選擇會決定整個架構，
做到一半才發現要改，等於重寫。

**所以動手前先回答下面五個問題。** 答不出來就是還沒想清楚，
這時候寫 RTL 只是在製造之後要丟掉的東西。

---

## 一、精度：多準才算對

**先定誤差容許範圍，再開始寫。** 沒定義的話會一路加嚴到做不完。

**選標準的順序 —— 從最鬆的開始，往上加到剛好夠用**：

| 標準 | 適用場合 | 成本 |
|---|---|---|
| 應用層結果一樣（文字、類別、畫面） | 神經網路推論、影像處理 | 低 |
| **在容許誤差內**（相對誤差 < 1e-6） | **大多數 DSP / AI 加速器** | 中 |
| 跟參考實作逐位元相同 | 金融、密碼學、需可重現 | 高 |
| 跟數學精確值一致 | **幾乎沒有** | 極高 |

最後一列是陷阱。`Fraction` 這種精確有理數**比 C 的 float 還嚴格** ——
C 的 `float a+b` 本身就有捨入誤差，拿精確值當標準等於追一個
連參考實作都達不到的目標。

**判斷依據**：

- **資料格式決定精度上限**。BF16 只有 7 bit 尾數（2-3 位十進位數字），
  FP16 是 10 bit，INT8 更少。**先看格式有幾位有效數字，再決定驗到多細。**
- **累加順序不同結果本來就會差**。軟體是循序 `for` 迴圈，
  硬體 PE array 常用樹狀平行加法 —— 最後幾個 bit 一定不同。
  那是**架構差異不是 bug**。
- **subnormal 通常可以不做**。很多商用加速器直接 flush-to-zero，
  對 AI 推論沒有可觀察的影響。做之前先問「不做會怎樣」。
- **特殊值（0/inf/NaN）跟精度是兩件事**。那是分支邏輯，分開驗。

## 二、面積：算得起才做得出來

**先估資源再設計算力**，不要寫完才發現塞不進去。

- **乘法器最貴**。Xilinx UltraScale+ 的 DSP48E2 是**定點的**（27×18），
  浮點乘法要用多個 DSP 拼或用 LUT。
  **先估「一個 PE 吃幾個 DSP」，才知道能開多少 PE。**
- **除法和取模不要用**。除非除數是 2 的冪（那會變成移位）。
  需要除法時想想能不能改成乘以倒數、或查表。
- **大範圍的優先編碼器很貴**。`for (i = 47; i >= 0; i--)` 找前導 1
  會展開成 48 級串接。分層（先看高 16 bit）或 `casez` 好很多。
  **但那是最佳化，先做對再說。**
- **記憶體分佈**：BRAM 有限、URAM 更少、外部 DDR 頻寬有限但容量大。
  資料放哪決定整個資料流架構。

## 三、時序：一個 cycle 能做多少事

**組合邏輯路徑越長，能跑的頻率越低。**

典型的長路徑（IEEE-754 加法）：
```
指數比較 → 對齊移位（桶形移位器）→ 加法 → 前導零偵測 → 正規化移位 → 捨入
```
全部串在一個 `always @*` 裡，在 100MHz 等級**很可能收不了時序**。

**做法**：
1. 先用純組合把**功能**做對（好除錯、好比對）
2. 確認數值正確後再切 pipeline
3. **切 pipeline 不改變數值結果**，只是把同一條路徑分到多個 cycle

**切在哪**：找路徑上「資料要重新排列」的點。
IEEE-754 加法器業界常見 2-3 級（對齊後 / 加法後 / 捨入前）。

⚠ 切了 pipeline 之後介面就有延遲了，testbench 要跟著改
（等 N 拍取結果，或加 valid/ready 交握）。
**別在功能還沒驗證之前切**，否則同時 debug 數值和時序兩件事。

## 四、頻寬：資料餵不進來，算力再強也沒用

**先算頻寬需求，再決定算力。** 這是最常被忽略的一環。

**算術強度**（arithmetic intensity）= 每讀一個 byte 能做幾次運算：

| 工作類型 | 算術強度 | 瓶頸 |
|---|---|---|
| 矩陣乘矩陣（大矩陣） | 高（O(n)） | 算力 |
| **矩陣乘向量（LLM 推論）** | **~2 FLOP/byte** | **記憶體頻寬** |
| 逐元素運算（加、ReLU） | < 1 | 記憶體頻寬 |

**memory-bound 的工作，加 PE 沒有用** —— 要做的是：
- 把資料放在頻寬高的那一側（權重放加速器端的 DDR，不要每次從主機搬）
- 提高資料重用（tiling、把 activation 留在暫存器）
- 壓縮資料（量化、稀疏）

**窄介面只傳小資料**。例如 STM32 透過 xSPI（~100-200 MB/s）接 FPGA：
權重放 FPGA 端的 DDR4，xSPI 只傳 activation（每層幾 KB）。
反過來每次搬 30MB 權重過去，加速器再快也沒意義。

**往返次數比單次頻寬更容易被忽略**。每次交易有固定協定開銷
（設定位址、等 busy、收尾）。12 次往返 × 0.3ms = 3.6ms，
可能比計算時間還久。**把整批工作一次送過去**，不要每個小步驟都來回。

## 五、介面：協定的複雜度要算進成本

- **AXI Full** 有五個通道（AW/W/B/AR/R）、burst、outstanding transaction。
  比自己定義的 valid/ready 難很多。**只有真的需要 burst 和亂序完成才用。**
- **AXI Lite** 適合暫存器存取（設定、狀態），單拍、沒有 burst。
- **AXI Stream** 適合連續資料流，沒有位址，最簡單。
- **自定 valid/ready** 在模組之間夠用，而且好驗證。

**選最簡單能滿足需求的**。介面協定的 bug 藏在時序交界處，
單看任何一個模組都看不出來，除錯成本很高。

## 六、動手前的檢查清單

寫第一行 RTL 之前，這六題要有答案：

```
1. 誤差容許多少？用什麼當比對標準？（外部的，不是自己寫的模型）
2. 資料格式幾位元？那決定了精度上限
3. 目標頻率多少？打算切幾級 pipeline？
4. 一個 PE 吃多少資源？總共開幾個？塞得下嗎？
5. 資料從哪來、頻寬夠不夠？算術強度是多少？
6. 介面用最簡單的哪一種就夠？
```

**答不出來就先去算、去查，不要先寫。**
硬體的錯誤成本比軟體高一個數量級 —— 架構選錯，寫再多都要丟掉。

---

## 七、驗證對象要是外部的

題目說「跟 X 一致」就真的去跑 X。

**不要拿自己寫的參考模型當唯一標準** —— 那是自己出題自己改考卷，
模型跟 RTL 可能一起錯，而且錯得一致。

自己的模型可以當**中間工具**（快速定位是哪一段錯），
但最終驗收要跟外部的東西比。詳見 [[verification-discipline]]。
